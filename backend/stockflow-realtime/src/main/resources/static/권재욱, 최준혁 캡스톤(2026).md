**캡스톤 구현 방안**

* **실시간 시세 캐싱**:  
  * 최신 주가 정보를 Redis에 저장 (TTL: 1초)

3.1 실시간 주가 데이터 수집 및 저장

3.2 시계열 분석 및 예측 모델 적용 

저장된 주가 데이터에 대해 결측치 처리, 이상치 제거 등의 전처리 과정을 수행한 후, 이 동 평균(Moving Average), 자기회귀(AR) 및 ARIMA 모델과 같은 대표적인 시계열 분석 알고리즘을 적용한다. 이를 통해 주가의 추세와 변동성을 분석하며, 분석 결과를 기반으로 단기 주가 예측 모델을 구현한다. 예측 결과는 시각화하여 사용자에게 직관적으로 제공한다.

3.3 대용량 데이터 처리 구조 설계 

여러 기업의 주가 데이터가 동시에 저장, 분석될 경우 발생할 수 있는 데이터베이스 부하 문제를 고려한다. 이를 해결하기 위해 효율적인 쿼리 설계, 캐싱 및 비동기 처리 구조를 적용하여 시스템의 안정성을 확보한다. 이를 통해 대용량 시계열 데이터 환경에서도 분석 과 예측 기능이 원활히 수행되도록 한다. 

3.4 예측 기반 백테스팅 기능 구현 

시계열 예측 결과를 실제 과거 데이터에 적용하여 백테스팅 기능을 구현한다. 예측 결과에 따른 단순 매매 전략을 설정하고, 누적 수익률 및 손실 지표를 계산하여 전략의 성능을 평 가한다. 이를 통해 예측 모델의 정확도를 검증한다.

| **①** | **외부 API → Python** | **Binance/Alpaca WebSocket으로 실시간 체결 데이터 수신** |
| **②** | **Python → Kafka** | **Python Producer가 원본 데이터를 정규화한 후 Kafka로 전송** |
| **③** | **Kafka → Spring Consumer** | **2개 Consumer Group이 동시 수신 (저장용 \+ 실시간용)** |
| **④** | **Consumer → TimescaleDB** | **저장용 Consumer가 Bulk Insert로 DB에 영구 저장** |
| **⑤** | **Consumer → Redis** | **실시간용 Consumer가 Redis에 최신가 캐싱 \+ Pub/Sub 발행** |
| **⑥** | **Redis → WebSocket → Client** | **Pub/Sub 메시지를 받아 STOMP WebSocket으로 클라이언트에 Push** |

# **2\. Kafka Topic 설계**

## **2.1 토픽 목록**

| Topic Name | 역할 | Retention |
| :---- | :---- | :---- |
| **market.raw.crypto** | **Binance 원본 JSON 보존 (디버깅용)** | **2시간** |
| **market.raw.stock** | **Alpaca 원본 JSON 보존 (디버깅용)** | **2시간** |
| **market.normalized** | **핵심 토픽: 정규화된 통합 데이터 (모든 Consumer가 구독)** | **4시간** |
| **market.dlq** | **처리 실패 메시지 보관 (Dead Letter Queue) → 구체화 필요** | **7일** |

## **2.2 raw vs normalized 관계**

**핵심 포인트: Kafka 내부에서 raw → normalized로 변환하는 것이 아니라, Python Producer가 정규화 한 후에 2곳으로 전송한다.**

 

**Python Producer 내부 처리 흐름:**

 

**Binance WebSocket 수신**

  **├── ① 원본 JSON 그대로 → market.raw.crypto (보험용)**

  **└── ② 정규화 변환 → market.normalized (실제 사용)**

 

**Spring Consumer들은 market.normalized만 구독한다.**

**raw 토픽은 문제 발생 시 원본 데이터 확인용으로만 사용.**

## **2.3 파티셔닝**

**모든 토픽의 파티션 키는 종목 심볼(symbol)을 사용한다.**

**이유: 동일 종목의 메시지가 항상 같은 파티션에 들어가므로 순서가 보장되고, Consumer별 병렬 처리도 가능하다.**

**→ 같은 파티션에 들어가면서 시간순 보장 가능**

**→ Consumer 개수가 파티션 개수를 동일하게 일정 분담하여 병렬 처리한다.**

# **3\. 데이터 정규화 (Normalization)**

**Binance와 Alpaca는 완전히 다른 JSON 포맷을 사용한다. 이를 통일된 스키마로 변환하여 하나의 Consumer로 모든 소스를 처리할 수 있게 한다.**

## **3.1 원본 데이터 비교**

**Binance와 Alpaca가 보내는 실제 데이터 포맷:**

| 필드 | Binance (암호화폐) | Alpaca (미국 주식) |
| :---- | :---- | :---- |
| **심볼** | **s: "BTCUSDT"** | **S: "AAPL"** |
| **가격** | **p: "67234.50"** | **p: 178.25 (숫자)** |
| **수량** | **q: "0.015"** | **s: 150 (정수)** |
| **시간** | **T: 1708234567890 (epoch ms)** | **t: "2025-03-15T14:30:00Z" (ISO)** |
| **거래소** | **없음 (Binance 고정)** | **x: "IEX" (거래소 명)** |

**→ 정규화를 시행한다.**

## **3.2 정규화 변환 규칙**

**Python Producer에서 다음 변환을 수행하여 통일된 스키마로 묶는다:**

| 변환 항목 | Binance → 통일 | Alpaca → 통일 |
| :---- | :---- | :---- |
| **가격** | **float("67234.50") → 67234.50** | **178.25 → 178.25 (변환 불필요)** |
| **수량** | **float("0.015") → 0.015** | **150 → 150 (변환 불필요)** |
| **타임스탬프** | **1708234567890 → 그대로 (epoch ms)** | **ISO 8601 → epoch ms 변환 (반대로도 가능)** |
| **거래소** | **"BINANCE" 고정값 추가** | **msg\["x"\] → "IEX", "NYSE" 등** |
| **시장 구분** | **"CRYPTO" 고정** | **"STOCK" 고정** |

# **4\. Spring Consumer DTO**

**Spring Kafka Consumer가 market.normalized 토픽의 JSON을 받을 때 사용하는 DTO 클래스:**

 

**@Data @Builder @NoArgsConstructor @AllArgsConstructor**

**public class NormalizedTradeDTO {**

 

    **@NotBlank**

    **private String source;   	// "BINANCE" | "ALPACA"**

 

    **@NotBlank**

    **private String symbol;   	// "AAPL", "BTCUSDT"**

 

    **@NotNull**

    **private BigDecimal price;	// 체결 가격**

 

    **@NotNull**

    **private BigDecimal volume;   // 체결 수량**

 

    **@NotBlank**

    **private String exchange; 	// 거래소 (BINANCE, IEX, NYSE)**

 

    **@NotNull**

    **private Long timestamp;  	// 체결 시간 (epoch ms)**

 

    **@NotNull**

    **private Long receivedAt; 	// Producer 수신 시각 (epoch ms)**

 

    **@NotBlank**

    **private String marketType;   // "CRYPTO" | "STOCK"**

**}**

 

| 필드 | 타입 | 용도 |
| :---- | :---- | :---- |
| **source** | **String** | **어느 API에서 온 데이터인지 구분** |
| **symbol** | **String** | **종목 식별자. Kafka 파티션 Key로도 사용** |
| **price** | **BigDecimal** | **체결 가격. 부동소수점 오차 방지를 위해 BigDecimal 사용** |
| **volume** | **BigDecimal** | **체결 수량. 암호화폐는 소수점, 주식은 정수** |
| **exchange** | **String** | **거래소 명. 미국 주식은 IEX, NYSE 등 다양** |
| **timestamp** | **Long** | **체결 시간 (UTC epoch ms). 모든 소스 동일 포맷** |
| **receivedAt** | **Long** | **Producer가 수신한 시간. End-to-End 레이턴시 측정용** |
| **marketType** | **String** | **시장 구분 (CRYPTO/STOCK). 프론트엔드 UI 분류에 활용** |

# **5\. Consumer Group 분리**

**Kafka의 Consumer Group 기능을 활용하여 하나의 토픽을 2개 그룹이 동시에 구독한다:**

| Consumer Group | 역할 | 처리 방식 |
| :---- | :---- | :---- |
| **storage-consumer-group** | **DB 저장 전담** | **최대 500건 묶어서 TimescaleDB Bulk Insert** |
| **realtime-consumer-group** | **실시간 Push 전담** | **건건이 즉시 Redis에 캐싱 \+ Pub/Sub 발행. 실시간성 우선** |
| **batch-consumer-group** | **배치 관련** | **데이터를 임시로 저장해둿다가 데이터 처리, 학습 관련 한번에 처리** |

**동일 메시지가 2개 그룹에게 동시 전달되는 구조.**

# **6\. Redis 캐싱**

**Realtime Consumer가 Kafka에서 받은 데이터를 Redis에 캐싱한다.**

**REST API 요청 시 DB를 조회하지 않고 Redis에서 즉시 반환한다.**

## **6.1 캐시 Key 설계**

| Key | Type | TTL | 용도 |
| :---- | :---- | :---- | :---- |
| **price:latest:AAPL** | **String (JSON)** | **60초** | **종목별 최신 체결 데이터 / 등락률 계산** |
| **price:prev-close:AAPL** | **String** | **24시간** | **전일 종가 (등락률 계산용)** |

## **6.2 캐싱 처리 흐름**

**Kafka에서 메시지를 받을 때마다 다음을 수행한다:**

 

**① NormalizedTradeDTO 수신 (symbol: AAPL, price: 178.25)**

**② Redis에서 전일 종가 조회**

**③ 등락률 계산**

**④ Redis에 최신가 캐싱 (TTL 60초)**

**⑤ REST API에서 /api/price/AAPL 요청 시 → DB 안 가고 Redis에서 즉시 반환 (\< 1ms)**

# **7\. Redis Pub/Sub 실시간 브로드캐스트**

**캐싱과 동시에 Pub/Sub로 메시지를 발행하여 WebSocket 클라이언트에게 실시간 Push한다.**

## **7.1 Pub/Sub 채널**

| 채널 패턴 | 설명 |
| :---- | :---- |
| **price:AAPL** | **종목별 실시간 가격 및 등락률 브로드캐스트** |

## **7.2 전체 처리 흐름**

 

**Kafka Consumer: 메시지 수신 → Redis SET (캐싱) \+ PUBLISH (브로드캐스트) 동시 수행**

**Redis: 채널에 구독 중인 MessageListener에게 메시지 전달**

**MessageListener: Redis에서 받은 메시지를 SimpMessagingTemplate로 WebSocket에 전달**

**Client: STOMP /topic/price/AAPL 구독 → 실시간 가격 업데이트**

**데이터 보관 정책 초안**

**1\. 배경**  
본 프로젝트는 실시간 주식 데이터를 수집/처리하는 구조로, 시간이 지날수록 데이터가 빠르게 증가한다. 효율적인 운영을 위해 장기 보관이 필요한 데이터는 DB에 저장하고, 빠른 조회가 필요한 데이터는 Redis 캐시로 관리하는 이중 구조를 적용한다.  
이에 따라 DB와 Redis 각각의 역할에 맞는 보관 정책을 수립한다.

**2\. 데이터 구분 및 보관 대상**

- 실시간 시세 원본 데이터 (DB)

예: market\_ticks의 체결가, 체결량, 체결시각 등 시계열 원천 데이터

- 운영/장애 대응 로그 데이터 (DB)

예: 애플리케이션 에러 로그, 배치 실행 로그, 시스템 이벤트 로그

- 서비스 운영 필수 데이터 (DB)  
  예: 사용자 계정 정보, 관심종목(Watchlist), 가격 알림 설정, 주문/체결 이력, 포트폴리오 상태, 종목 기본정보(티커/종목명)  
- 고속 조회용 캐시 데이터 (Redis)

예: 최신 시세, 인기 종목 목록, 최근 조회 결과, 임시 세션/상태값

**3\. 보관 정책(안)**  
DB와 Redis의 역할에 맞춰 다음과 같이 적용.

* DB \- 실시간 시세 원본 데이터: 최근 3개월 보관  
  * 3개월 초과 데이터는 삭제하거나, 필요 시 요약 데이터만 유지  
* DB \- 운영 로그 데이터: 최근 1개월 보관  
  * 장애 분석 최소 기간만 보관 후 자동 정리  
* DB \- 서비스 운영 필수 데이터: 장기 보관  
  * 서비스 기능 유지와 사용자 이력 관리에 필요하므로 상시 유지  
* Redis \- 캐시 데이터: 단기 보관(TTL 기반 자동 만료)  
  * 최신 시세/조회 캐시: 예) 수초\~수분  
  * 세션/임시 상태값: 예) 수분\~수시간  
  * Redis 데이터는 영구 보관 대상이 아니며, 만료 시 DB/재수집 데이터로 재생성

**4\. 운영 방식**  
DB 보관 만료 데이터는 정기 스케줄러(예: 주 1회)로 정리한다.  
대량 삭제 전 백업 스냅샷을 수행해 복구 가능성을 확보한다.  
Redis는 키 단위 TTL을 기본 적용하고, 만료 정책(EXPIRE)으로 자동 정리한다.  
DB는 정합성(기준 데이터), Redis는 성능(고속 조회) 역할로 분리 운영한다.  
데이터 증가량, 조회 성능, 캐시 적중률을 월 단위로 점검해 보관 기간과 TTL을 조정한다.

**DB 설계 · 유저 시나리오 요약**

우리 서비스는 바깥에서 실시간 시세를 받아서 Kafka로 보내고, DB에는 쌓아 두고, 화면에 빨리 보여 줄 부분은 Redis를 쓰는 구조. 아래는 “사용자가 뭘 할 때” 그걸 받치려고 DB를 어떻게 잡았는지를 쉽게 정리한 것이다.

* 실시간으로 가격만 빨리 보고 싶을 때

매번 DB를 뒤지면 느려질 수 있어서, 최신 가격은 Redis에 두고 WebSocket으로 밀어줌. 그래도 나중에 감사·분석을 위해 체결 데이터 자체는 DB(\`market\_ticks\`)에 계속 쌓는다.

* 과거 차트나 예전 가격을 보고 싶을 때

체결 한 건 한 건이 모인 게 \`market\_ticks\`이고, 1분 단위로 묶어 둔 요약본이 \`market\_ticks\_1m’. 차트를 그릴 때는 이걸 쓰면 전체를 다 훑지 않아도 됨.

* 어떤 종목인지(코인인지 주식인지, 어느 거래소인지) 맞춰 두고 싶을 때 

\`instruments\` 테이블에 종목 정보를 두고, 데이터가 들어올 때마다 갱신해 주는 처리. (나중에 여유 되면, 틱이랑 종목표가 완전히 맞는지 돌려보는 배치는 추가 가능.)

* 회원 가입하고 관심 종목만 모아 보고 싶을 때

\`users\`랑 \`user\_watchlist\` 테이블을 만들어 두었음. 실제 로그인·회원 API까지는 일정에 맞춰 붙일 예정.

* 데이터가 늦게 들어왔는지 확인하고 싶을 때  

같은 행에 체결 시각(\`ts\`)과 우리 DB에 저장된 시각(\`ingested\_at\`)을 나눠 두었음. 둘 차이를 보면 파이프라인이 얼마나 밀렸는지 대략 알 수 있음.

* 나중에 일봉으로 분석하거나 백테스트할 때

하루 단위 요약(\`symbol\_daily\_ohlcv\`)과 배치가 돌았는지 기록(\`batch\_job\_runs\`)용 테이블만 만들어 둠. 안에 데이터를 채우는 Job은 앞으로 구현 예정.

* 정리

가입·관심종목 같은 건 일반 DB 테이블로, 지금 가격은 Redis로 빠르게, 지난 시세·차트는 시계열 DB에 쌓아 두는 식으로 나눔.

**기술적 지표 계산 서비스 (TechnicalIndicatorService) 명세**

 

#  **핵심 설계 포인트 (Key Features)**

## **정밀한 금융 수학 계산 (BigDecimal)**

• 	부동소수점 오차(예: 0.1 \+ 0.2 \= 0.300000004)를 방지하기 위해 모든 계산을 BigDecimal로 처리합니다.

 

## **OHLCV 기반 확장 계산**

• 	기존에는 종가(Close)만 사용했으나, 볼린저 밴드·스토캐스틱·ATR·OBV 지표 추가를 위해 OhlcvData 레코드를 도입하여 시가/고가/저가/종가/거래량 전체를 활용합니다.

• 	computeWithOhlcv() 메서드를 통해 모든 지표를 한 번의 호출로 계산합니다.

 

#  **지표별 상세 계산 로직**

## **1\. 통합 계산 메서드 (computeWithOhlcv)**

• 	역할: 외부(Batch Tasklet)에서 호출하는 단일 진입점

• 	입력: List\<OhlcvData\> — 오래된 순 → 최신 순으로 정렬된 OHLCV 데이터

• 	동작: 입력받은 OHLCV 리스트를 바탕으로 아래 11개 지표를 한 번에 계산하여 DailyIndicatorItem 객체(DTO)로 반환

 

| 카테고리 | 지표 | 필요 데이터 |
| :---- | :---- | :---- |
| 이동평균 | MA5, MA20, MA60 | 종가 |
| 모멘텀 | RSI14 | 종가 |
| 추세 | MACD, Signal, Histogram | 종가 |
| 변동성 | 볼린저 밴드 (Upper, Lower) | 종가 |
| 모멘텀 | 스토캐스틱 (%K, %D) | 고가, 저가, 종가 |
| 변동성 | ATR14 | 고가, 저가, 종가 |
| 거래량 | OBV | 종가, 거래량 |

 

## **2\. 단순 이동평균 (SMA \- Simple Moving Average)**

• 	메서드: sma(closes, period)

• 	용도: 가격의 평균적인 흐름을 파악하여 현재 가격이 평균보다 높은지/낮은지 판단

• 	로직: 전체 종가 리스트 중 가장 최근의 period일(예: 5일, 20일, 60일)만큼 잘라내어 합산 후 period로 나눔

 

## **3\. 지수 이동평균 (EMA \- Exponential Moving Average)**

• 	메서드: ema(closes, period)

• 	용도: SMA보다 최근 가격에 더 민감하게 반응하여 빠른 추세 전환 포착

• 	가중치(Multiplier) \= 2.0 / (period \+ 1\)

• 	초기값: 첫 period일의 SMA

• 	점화식: EMA(today) \= (종가 × 가중치) \+ (EMA(yesterday) × (1 \- 가중치))

## **4\. 상대강도지수 (RSI \- Relative Strength Index)**

• 	메서드: rsi(closes, period) — 기본 14일

• 	용도: 현재 시장이 과매수(Overbought) / 과매도(Oversold) 상태인지를 0\~100 사이의 수치로 표현

**계산 순서:**

• 	1단계: 전일 대비 변화량 계산 — 상승일: Gain \= 당일종가 \- 전일종가 / 하락일: Loss \= 전일종가 \- 당일종가

• 	2단계: Wilder's Smoothed Average — 첫 14일은 단순 평균, 이후 AvgGain \= (이전AvgGain × 13 \+ 당일Gain) / 14

• 	3단계: RS \= AvgGain / AvgLoss

• 	4단계: RSI \= 100 \- (100 / (1 \+ RS))

• 	예외 처리: 하락분이 0이면(연속 상승) RSI \= 100 반환

 

## **5\. MACD (이동평균 수렴발산)**

추세의 방향과 강도를 동시에 보여주는 지표로, 3가지 컴포넌트로 구성됩니다.

### **5-1. MACD 라인 (macdLine)**

• 	공식: EMA(12) \- EMA(26)

• 	의미: 단기 추세와 장기 추세의 차이. 양수면 상승 모멘텀, 음수면 하락 모멘텀

• 	필요 데이터: 최소 26일

### **5-2. MACD 시그널 (macdSignal)**

• 	공식: MACD 라인의 EMA(9)

• 	로직: 과거 데이터를 순회하며 각 시점의 MACD 라인 값으로 macdSeries 생성 → EMA(9) 적용

• 	필요 데이터: 최소 34일 (26 \+ 9 \- 1\)

### **5-3. MACD 히스토그램 (macdHist)**

• 	공식: MACD 라인 \- MACD 시그널

• 	MACD가 시그널선을 상향 돌파 → 매수 신호 (골든크로스)

• 	MACD가 시그널선을 하향 돌파 → 매도 신호 (데드크로스)

 

## **6\. 볼린저 밴드 (Bollinger Bands)**

• 	메서드: bollingerUpper(closes), bollingerLower(closes)

• 	필요 데이터: 최소 20일

• 	Middle Band \= MA(20) — 기존 ma20 컬럼 재사용

• 	Upper Band \= MA(20) \+ (2 × 20일 표준편차)

• 	Lower Band \= MA(20) \- (2 × 20일 표준편차)

 

## **7\. 스토캐스틱 (Stochastic Oscillator)**

• 	메서드: stochasticK(ohlcvList), stochasticD(ohlcvList)

• 	용도: 현재 종가가 최근 N일간의 가격 범위 중 어디에 위치하는지를 백분율로 표시

• 	필요 데이터: %K는 14일, %D는 16일 (14 \+ 3 \- 1\)

• 	%K \= (현재 종가 \- 14일 최저가) / (14일 최고가 \- 14일 최저가) × 100

• 	%D \= %K의 3일 단순이동평균(SMA)

• 	예외 처리: 최고가 \= 최저가인 경우(변동 없음) %K \= 50 반환

 

## **8\. ATR (Average True Range \- 평균 진정 범위)**

• 	메서드: atr(ohlcvList, period) — 기본 14일

• 	용도: 가격의 변동성(Volatility) 수치화. 손절매 폭, 포지션 크기 결정에 활용

• 	필요 데이터: 최소 15일 (14 \+ 전일종가 1일)

• 	True Range \= MAX(당일 고가 \- 당일 저가, |당일 고가 \- 전일 종가|, |당일 저가 \- 전일 종가|)

• 	ATR(14) \= 최근 14일간 TR의 단순이동평균(SMA)

 

## **9\. OBV (On Balance Volume \- 누적 거래량)**

• 	메서드: obv(ohlcvList)

• 	용도: 거래량의 흐름을 누적하여 가격 움직임의 선행 지표로 활용

• 	필요 데이터: 전체 히스토리 (많을수록 정확)

# **🔧 지표별 처리 방식 (SQL vs Java)**

## **현재 구현 현황**

 

| 지표 | SQL 가능 여부 | 실제 처리 위치 | 비고 |
| :---- | :---- | :---- | :---- |
| MA5, MA20, MA60 | ✅ 가능 | Java | SMA는 SQL AVG()로 가능하나 통일성 위해 Java |
| RSI14 | ❌ 불가 | Java | Wilder's Smoothing 재귀 계산 필요 |
| MACD / Signal / Hist | ❌ 불가 | Java | EMA 재귀 계산 필요 |
| 볼린저 밴드 | ✅ 가능 | Java | AVG() \+ STDDEV() 윈도우 함수 |
| 스토캐스틱 | ✅ 가능 | Java | MIN(), MAX() 윈도우 함수 |
| ATR | ✅ 가능 | Java | LAG() \+ GREATEST() |
| OBV | ✅ 가능 | Java | CASE WHEN \+ SUM() OVER() |

 

현재 상태: SQL은 데이터 조회와 저장(UPSERT)만 담당하고, 모든 지표 계산은 Java에서 처리

 

## **SQL로 처리 가능하지만 Java로 구현한 이유**

 

| 이유 | 설명 |
| :---- | :---- |
| 코드 일관성 | RSI, MACD는 반드시 Java 필요 → 나머지도 같은 위치에서 처리 |
| 정밀도 | BigDecimal(18자리)로 금융 계산 오차 최소화 |
| 디버깅 용이 | 중간 계산 과정 로깅 및 단위 테스트 가능 |
| 유지보수 | 지표 추가/수정 시 한 곳(Service)만 변경 |

# **핵심 설계 포인트 (Key Features)**

## **다중 데이터 소스 통합 (Multi-Source Integration)**

• 	Redis 캐시에서 실시간 가격 데이터를 \< 1ms 응답으로 제공합니다.

• 	TimescaleDB에서 과거 OHLCV 및 기술적 지표 데이터를 조회합니다.

• 	PostgreSQL에서 종목 마스터 정보(instruments)를 관리합니다.

• 	각 데이터 소스의 특성에 맞게 최적화된 조회 방식을 적용합니다.

 

## **Batch Job 연계 (Batch Integration)**

• 	일일 배치 작업에서 계산된 OHLCV 집계 및 기술적 지표를 API로 노출합니다.

• 	MA5/20/60, RSI14, MACD, 볼린저 밴드, 스토캐스틱, ATR, OBV 등 11개 지표를 제공합니다.

• 	배치에서 계산된 데이터는 symbol\_daily\_ohlcv, symbol\_daily\_indicators 테이블에 저장됩니다.

 

## **실시간 가격 조회 (Real-time Price)**

• 	Kafka로 수집된 실시간 틱 데이터가 Redis에 캐싱됩니다.

• 	PriceController를 통해 DB 조회 없이 즉시 최신 가격을 반환합니다..

 

## **Swagger API 문서화**

• 	SpringDoc OpenAPI를 통해 모든 API가 자동 문서화됩니다.

• 	/swagger-ui.html에서 API 테스트 및 스펙 확인이 가능합니다.

| API 레이어 | REST API (Price / Stock / Indicator / Market) | 클라이언트 데이터 제공 |

**StockFlow — 종목 등록 및 DB 구조 정리**

# **1\. 종목 등록은 자동**

사용자가 종목 등록 API를 한 번도 호출하지 않아도 종목이 DB에 쌓이는 이유는, 실시간 시세 데이터가 들어올 때마다 시스템이 자동으로 종목을 등록하기 때문임.

시세 수신 파이프라인을 건드리는 게 아니라, 그 옆에 instruments(종목 마스터 테이블)를 동기화해주는 별도 흐름이 함께 돌고 있는 구조임.

 

# **2\. 두 가지 흐름이 동시에 동작**

## **① 자동 등록 흐름 (실시간 시세 → 종목 마스터 자동 동기화)**

실시간 시세 메시지 도착 (NormalizedTradeDTO)

→ registerDistinctFromTrades(trades) 호출

→ 각 trade에서 symbol / marketType / exchange 추출

→ SELECT register\_instrument(symbol, marketType, exchange, name)  ← Postgres 함수

→ instruments 테이블에 UPSERT

 	\- 신규:

 INSERT (name \= symbol로 임시 등록)

 	\- 기존: last\_seen\_at 갱신

 

시세가 들어올 때마다 "이 종목 봤다"고 DB에 알리는 구조이며, DB 함수가 신규/기존을 판단해서 처리함.

자동 등록된 종목은 처음엔 name \= symbol (예: name="AAPL") 로 들어감.

(효율성 고려하여 하루에 한 번하는 식으로 조정 고려)

 

## **② 수동 관리 API (StockController)**

| 엔드포인트 | 하는 일 |
| ----- | ----- |
| GET /api/stocks | instruments 목록 \+ Redis 최신 가격 합쳐 반환 |
| GET /api/stocks/{symbol} | 위와 동일, 단일 종목 |
| POST /api/stocks | register\_instrument UPSERT 호출 (사람이 직접 이름 지정 가능) |
| PUT /api/stocks/{symbol} | 표시 이름(name), 거래소(exchange) 컬럼만 UPDATE |
| DELETE /api/stocks/{symbol} | is\_active \= false 소프트 삭제 |
| GET /api/stocks/{symbol}/ohlcv | 일봉 OHLCV 시계열 조회 |
| GET /api/stocks/{symbol}/indicators | 일봉 지표 시계열 조회 |

 

POST: 시세가 아직 안 들어온 종목을 선제적으로 등록하거나 처음부터 이름을 지정하고 싶을 때 사용. 이미 존재하면 정보가 업데이트됨.

PUT: 자동 등록으로 name \= "AAPL"처럼 심볼 그대로 들어간 이름을 "애플"로 바꾸는 등 메타데이터 보정 용도. 시세/OHLCV 데이터에는 손대지 않음.

 

# **3\. TimescaleDB는 별도 DB 아님**

TimescaleDB는 PostgreSQL 위에 올라간 확장(extension)임. 즉 하나의 Postgres 인스턴스 안에 일반 테이블과 Timescale 하이퍼테이블이 함께 존재함.

**백테스팅 엔진 (Backtesting Engine) 명세**

시계열 일봉 데이터(symbol\_daily\_ohlcv)를 기반으로 매매 전략을 과거 구간에 적용하고, 누적 수익률·MDD·승률 등 성과 지표를 산출하여 전략의 유효성을 검증하는 모듈입니다. 전략을 저장(CRUD)해 두고 반복 실행할 수도 있고, 저장 없이 즉석(ad-hoc)으로 실행할 수도 있습니다.

# **핵심 설계 포인트 (Key Features)**

## **일봉 기반 시뮬레이션 (Daily Bar Simulation)**

• 	배치 Job이 집계한 symbol\_daily\_ohlcv(일봉)를 입력으로 사용하여, 실시간 틱과 분리된 안정적인 백테스트 입력 계층을 확보합니다.

• 	같은 종목·일자에 여러 source가 존재할 수 있으므로, 일자별로 가장 최근 계산본(computed\_at DESC) 하나만 DISTINCT ON으로 선택합니다.

## **정밀한 자산 계산 (BigDecimal)**

• 	현금·수량·평가금액 등 모든 금액 계산은 BigDecimal(MathContext.DECIMAL64)로 처리하여 부동소수점 오차를 방지합니다.

• 	매매 신호 판단(이동평균 비교, RSI 임계값)은 비교 연산이므로 double로 계산하여 단순성을 유지합니다.

## **전략-엔진 분리 (Strategy / Engine Separation)**

• 	전략(TradingStrategy)은 "시점별 매매 신호(BUY/SELL/HOLD)"만 생성하고, 실제 체결·자산 평가·지표 산출은 엔진(BacktestEngine)이 전담합니다.

• 	신호 i는 bars\[0..i\]의 정보만 사용하여 미래 참조(look-ahead bias)를 방지합니다.

# **지원 전략 (Strategy Types)**

| 전략 타입 | 설명 | 파라미터 (기본값) |
| :---- | :---- | :---- |
| **BUY\_AND\_HOLD** | 첫 거래일 전량 매수 후 끝까지 보유 (벤치마크) | 없음 |
| **MA\_CROSSOVER** | 골든크로스 매수 / 데드크로스 매도 | shortPeriod(5), longPeriod(20) |
| **RSI** | RSI 과매도 매수 / 과매수 매도 | period(14), oversold(30), overbought(70) |

# **엔진 동작 규칙 (Execution Model)**

롱-온리(long-only), 전량 매수/전량 매도(all-in / all-out) 방식의 단순 매매를 시뮬레이션합니다.

• 	현금 보유 중 BUY 신호 → 해당 봉의 종가로 전량 매수 (분할 수량 허용)

• 	주식 보유 중 SELL 신호 → 해당 봉의 종가로 전량 매도

• 	보유 중 BUY, 현금 중 SELL 등 무효 신호는 무시 (엔진이 포지션 상태로 필터링)

• 	매 봉마다 평가금액(equity \= 현금 \+ 보유수량 × 종가)을 계산하여 자산 곡선과 낙폭을 기록

# **성과 지표 (Performance Metrics)**

| 지표 | 설명 | 계산식 |
| :---- | :---- | :---- |
| **총 수익률 (totalReturnPct)** | 초기 자본 대비 누적 수익률 | (최종 평가금액 − 초기 자본) / 초기 자본 × 100 |
| **CAGR (cagrPct)** | 연평균 복리 수익률 | (최종/초기)^(1/연수) − 1, ×100 |
| **MDD (mddPct)** | 최대 낙폭 | max((고점 − 평가금액) / 고점) × 100 |
| **거래 횟수 (tradeCount)** | 완료된 라운드트립(매수→매도) 수 | SELL 체결 건수 |
| **승률 (winRatePct)** | 이익 라운드트립 비율 | 이익 거래 / 라운드트립 × 100 |

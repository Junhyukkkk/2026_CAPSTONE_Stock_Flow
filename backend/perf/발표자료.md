## 1. 배경 — "토스증권처럼 미국 주식 시세를 끊김 없이"

- 증권 앱의 시세 화면은 **모든 종목의 체결이 장 시작 직후 한꺼번에 몰려도** 밀리지 않아야 한다.
- 시세는 한 번 놓치면 되돌릴 수 없다. 느려지는 것보다 **조용히 빠지는 것**이 더 위험하다.
- 우리 목표: "미국 주식 전 종목 체결을 증권사처럼 받아낼 수 있는 파이프라인"을 학교 서버 한 대(8코어/15GB/HDD)에서 증명한다.

## 2. 요구사항을 숫자로 바꾸면

| 요구 | 기준 | 달성 |
|---|---|---|
| 처리량 | 장 시작 피크에서도 적체 없음 | 12,000건/초까지 적체 없음 |
| 지연 | 체결 → 화면 | 약 12ms (로컬, 개선 전 61ms) |
| 무손실 | 포화·장애에도 데이터 보존 | Kafka 버퍼, 보관 4시간 내 복구 시 유실 0 |
| 분석 | 시세가 몰려도 사용자 요청은 빠르게 | 예측 API 중앙값 약 1초 |
| 비용 | 실데이터 구독은 비싸다 | 실제형 시뮬레이터로 부하·기능 검증 |

> **솔직한 전제**: 미국 전 종목 실데이터는 유료(Alpaca 무료 플랜은 IEX 단일 거래소·동시 30종목)라 구독하지 않았다.
> 대신 실제 종목·가격대·장중 체결 곡선을 따라 하는 시뮬레이터로 부하를 만들었고, 그 부하로 용량을 쟀다.
> 참고: 미국 전체 시세(SIP)는 호가를 포함해 Tape A·B 만으로 2026년 1분기 피크 초당 약 138만 메시지([CTA 공개 지표](https://www.ctaplan.com/publicdocs/ctaplan/CTAPLAN_Processor_Metrics_1Q2026.pdf)) — **체결만 받는 우리 파이프라인이 곧바로 전체 시장 용량을 뜻하지는 않는다.** 용량은 수평 확장(프로세스 분리, 파티션 증설)의 출발점으로 읽어야 한다.

## 3. 아키텍처 — 컨베이어 벨트

```
Binance(코인 757종목) ─┐
Alpaca IEX(미국 30종목) ─┼→ Kafka(market.normalized, 12파티션)
미국 주식 시뮬레이터 ───┘        │
                                 ├→ realtime-group → Redis(최신가 SET + Pub/Sub) → WebSocket → 화면
                                 └→ storage-group  → TimescaleDB(market_ticks, 1분봉 집계, 일봉·지표)
                                                          └→ 분석 서비스(FastAPI: ARIMA·Chronos) → 예측 API
```

| 공정 | 기술 | 포인트 |
|---|---|---|
| 수집 | Python | 정규화해 한 포맷으로 |
| 전달 | Kafka | 버퍼 — 밀려도 디스크에 쌓임 |
| 실시간 | Redis·WebSocket | 최신가 + 발행 |
| 저장 | TimescaleDB | 하이퍼테이블, 압축 7일, 보관 400일 |
| 분석 | FastAPI | 코어·메모리 예약 |

## 4. 어떻게 쟀나 — 측정 방식이 곧 신뢰도

1. **실제 같은 부하기**: 처음엔 가짜 종목(SYM000…)을 균등하게 쏘는 도구였다. 이제는 **실제 종목·가격대·장중 체결 곡선(장 시작/마감 몰림)**을 따라 하는 시뮬레이터 → `source=SIMLOAD` 라벨로 운영 데이터와 분리.
2. **같은 조건에서 코드만 교체**: 파티션 12·Redis 2GB·서버 고정, 앱 이미지만 7/8 → 9/21 → 10/5 버전으로 바꿔 끼움.
3. **같은 시간대에 연속 측정**: 공용 서버라 절대값이 시간대에 따라 최대 2배 흔들린다 → 상대 비교만 근거로 사용.
4. **판정 기준**: 소비율 · peak lag · 부하 종료 후 배수 시간.
5. **부하 중 분석 API 응답시간까지 같이 측정**.

> 배운 점(7월): 부하기를 "초 시작마다 몰아서" 쏘았더니 시스템이 느린 것처럼 보였다. **측정 도구가 결과를 왜곡할 수 있다.** 균등 발사로 고쳐서 비로소 실제 성능이 보였다.

| 9/7~20 | 약 4,000→8,000/s | 로그 폭주(DEBUG), Redis 왕복 | 로그 INFO, 파이프라인, WS 스레드풀 |

## 7. 최적화 표 — 무엇이 얼마나 올렸나

| 최적화 | 효과 |
|---|---|
| Redis 커넥션 풀 | 소비 523 → 2,453 @7,000/s (**4.7배**) |
| 로그 DEBUG → INFO | 2,453 → 6,176 (같은 부하) |
| Redis 파이프라인(SET+PUBLISH 1왕복) | 끄면 −19% |
| WebSocket 전송 고정 스레드풀 | 끄면 −73% |
| 종목 재등록 캐시 + 예외 제거 | DB 쓰기 495,652 → 100회, 저장 처리 5.2 → 1.1ms |
| **저장 경로 묶음**: 멱등성 TTL 24h→10분 · 컨슈머 배치(500) · JDBC 멀티로우 INSERT · Lettuce 풀 48 · Hikari 24 · 멱등성 파이프라인 | 저장 소비 **6,000 → 9,000 (+50%)**, 상한 6,600 → 14,000 |
| Kafka 파티션 6 → 12 | 컨슈머 스레드 12/12 활성 |

**포인트 두 가지**
- 저장 묶음은 *하나씩은 노이즈, 합쳐야 2배* — 병목이 한 곳이 아니라 겹쳐 있었다. (단독 측정만 했다면 "효과 없음"으로 버렸을 것)
- **해보고 버린 것**도 기록: 컨슈머 동시성 축소(−17%), JVM 힙 고정(−21%), 실시간 배치 소비·E2E 샘플링(이득 없음), `synchronous_commit=off`(내구성 대비 이득 작음).

## 9. 포화돼도 터지지 않고, 유실은 미리 알린다

- 20,000건/초(용량의 약 1.7배)를 90초 투입 → 앱 크래시·OOM **없음**, 초과분은 Kafka 디스크에 쌓였다가 **23초 만에 배수**.
- 진짜 위험은 크래시가 아니라 **보관기간(4시간)을 넘겨 조용히 사라지는 것** → 지표(`consumer_lag`, `retention_margin`) + 3단계 경보 → **Discord 실시간 알림**. 9/20 Redis 장애 때 실제로 작동해 적체 1,300만 건을 유실 없이 복구.

## 10. 분석 서비스에 용량을 따로 떼어두기

- 문제: 시세가 몰리면 CPU를 다 써서 사용자가 누른 **예측 요청이 느려질 수 있다**.
- 해결: 8코어 중 **코어 6–7과 메모리 3GB를 분석 컨테이너 전용으로 예약**, 나머지 컨테이너는 코어 0–5 (`reserve-analysis-capacity.sh`).
- 검증: 파이프라인을 4,000 → 20,000건/초로 올리는 동안 예측 API를 계속 호출

| 파이프라인 부하 | 호출 | 성공 | 응답 중앙값 | 최대 |
|---:|---:|---:|---:|---:|
| 4,000 | 5 | 5 | 1.1초 | 7.8초(첫 학습) |
| 10,000 | 6 | 6 | 0.7초 | 1.2초 |
| 20,000 (포화) | 6 | 6 | 0.8초 | 1.1초 |

> 첫 호출만 모델 학습으로 10~15초, 이후는 캐시되어 약 1초. 예측 결과는 이제 **자동으로 DB 에 저장**된다(§12).

## 12. 주목할 만한 기능 3가지

1. **실제형 미국 주식 시뮬레이터** — 종목별 일 체결 수 비례 도착률(Poisson), 장 시작/마감 U자 곡선, 가격 평균회귀 모델, 시작가는 Alpaca 스냅샷. 데이터 라벨(`SIMULATOR`)로 실데이터와 분리, 실데이터 라벨 사용은 거부. *"돈 안 드는 전 종목급 부하기"*
2. **예측 자동 저장** — 비동기·제한 큐, 저장이 느려도 응답은 그대로, 같은 기준 봉은 한 번만. 나중에 실제값과 조인해 **적중률 비교** 가능.
3. **용량 예약 + 상시 경보** — 분석 요청 전용 코어, 유실 임박 Discord 알림.

## 13. 운영에서 배운 것 — Redis 인시던트 (9/20)

- 증상: 적체 경보 → 1차 가설(파이프라인 버그)로 옵션을 껐지만 그대로.
- 원인: 스택트레이스 `Caused by` 끝까지 읽으니 `READONLY … replica` — **인증 없이 열린 Redis 포트에 외부 봇이 replica 명령을 주입**.
- 복구: `REPLICAOF NO ONE`, 적체 1,300만 건 유실 없이 배수.
- **남은 과제(미조치)**: `requirepass` 설정, 6379 포트 외부 차단.
- 교훈: "처음 떠오른 가설에 만족하지 말 것" — 성능 분석에서 얻은 태도(측정 먼저)가 장애 대응에도 그대로 통했다.

| 단일 서버 | 공용 서버라 시간대에 따라 절대값이 최대 2배 흔들림 → 상대 비교로만 인용 |
| 미배포 | 저장 경로 최적화·예측 자동 저장·시뮬레이터는 브랜치 상태(병합·배포 전). 라이브 Redis 는 TTL 24시간 설정 때문에 2GB 가득 참 → 배포 시 해소 |
| 보안 | Redis 인증·포트 차단 미완 |
| 디스크 | 단일 HDD — 대량 삭제·집계가 겹치면 iowait 급증 (실제 겪음) |

**다음 단계**: 최적화 병합·배포 → Redis 인증 → 시뮬레이터를 장중 곡선 그대로 상시 가동(×1) → 프로세스 분리(`--profile split`) 부하 검증 → NTP 동기화.

## 15. 배운 점

1. **측정이 먼저다.** 예측한 병목의 절반은 틀렸고, 가장 큰 원인은 예측 목록에 없었다.
2. **병목은 이동한다.** 하나를 풀면 다음 자원이 새 상한 — 그래서 매번 같은 방식으로 재측정.
3. **단독 효과와 조합 효과는 다르다.** 하나씩은 노이즈, 합치면 2배.
4. **측정 도구도 검증 대상이다.** 부하기·측정 시간대·표본 수가 결과를 바꾼다. 같은 시간대 교차 측정으로만 비교.
5. **실패한 시도도 기록한다.** 안 된 6가지가 된 6가지만큼 설계 근거가 됐다.

## 부록 B. 예상 질문

**Q. 미국 전 종목을 정말 다 받나?** 실데이터 전 종목은 구독 비용 때문에 받지 않았다(Alpaca 무료는 IEX·30종목). 실제형 시뮬레이터 부하로 용량을 증명했고, 평균 14배·피크 5배 여유를 확인했다. 전체 시장 규모는 확장 설계가 필요하다고 §2·§14에 밝혔다.

**Q. 12,000건이면 충분한가?** 우리 가정의 부하(832/s 평균, 2,400/s 피크) 기준으로는 충분하다. 전체 시장(호가 포함 SIP 피크 140만 msg/s)에는 한 대로 부족하다 — 체결만, 종목 범위를 정해 받는 구조.

**Q. 왜 시뮬레이터인가?** 전 종목 유료 구독 비용 + 장외 시간에도 24시간 반복 측정이 필요해서. 실데이터와 라벨로 분리해 섞이지 않게 했다.

**Q. 측정이 믿을 만한가?** 90초 표본 ±10%, 시간대 편차가 있다. 그래서 같은 시간대 교차 측정만 비교에 썼고 절대값은 인용하지 않는다.

**Q. 분석이 느려지지 않나?** 코어 6–7·메모리 3GB 예약으로 포화 부하에서도 중앙값 약 1초(§10). 첫 호출은 모델 학습으로 10~15초.

**Q. 왜 Redis 가 뚫렸나?** 인증 없이 포트를 외부에 노출한 배포 설정 문제. 재발 방지(비밀번호·포트 차단)는 남은 과제.

## 1. 무엇을 하는 시스템인가

거래소에서 들어오는 시세를 실시간으로 받아 화면에 뿌리고, 동시에 DB에 저장하는 파이프라인.

데이터는 컨베이어 벨트처럼 여러 공정을 거친다.

```
[수집] → [전달: 메시지 큐] → [실시간 처리: 임시 저장소] → [화면 전송]
                                    │
                                    └→ [영구 저장: DB]  (옆으로 갈라짐)
```

| 공정 | 역할 | 사용 기술 |
| --- | --- | --- |
| 수집 | 거래소 데이터를 받아옴 | Python |
| 전달 | 공정 사이를 잇는 메시지 큐 | Kafka |
| 실시간 처리 | 최신가 계산·캐싱·발행 | Redis |
| 화면 전송 | 브라우저로 밀어줌 | WebSocket |
| 영구 저장 | 시세를 기록 | TimescaleDB |

## Part 2 — 성능 분석 (로컬 측정, 7월)

## 3. 문제 제기

화면에 시세가 뜨는 게 느리다. 그런데 **어디가 느린지 알 수 없었다.**

기존 계측은 "처음부터 끝까지 몇 ms" 하나뿐이었다. 느리다는 건 알아도 어느 공정 탓인지 짚을 수 없었다.

그래서 병목이 있을 만한 곳을 **8가지로 예측**했다.

- 배치 flush 대기 · Kafka 설정 · Redis 왕복 횟수 · 실시간과 저장의 결합
- Producer 전송 방식 · 파티션 수 · DB 연결 수 · 전송 대기 시간

---

## 4. 접근 — 고치기 전에 측정부터

예측만 믿고 고치면 엉뚱한 곳에 시간을 쓴다. **측정을 먼저** 하기로 했다.

세 가지 도구를 만들었다.

### ① 공정마다 스톱워치

각 구간의 시작과 끝에 시각을 찍어 걸린 시간을 기록. 총 11개 구간.

```
long start = 시작();
작업 수행();
기록(구간이름, start);      // 걸린 시간이 저장소에 쌓임
```

- 나노초 단위로 측정 (Redis 명령이 0.1ms라 밀리초로는 0이 된다)
- 개별 값을 다 저장하지 않고 횟수·총합만 누적 → 평균은 나중에 나눗셈
- `/actuator/prometheus` 주소로 밖에서 조회

**전체와 부분을 같이 재둔 게 핵심.** "저장 전체 5.2ms 중 종목 등록이 3.0ms"라는 걸 두 값을 나란히 놓고 알았다.

### ② 부하 생성기

가짜 시세를 일정한 속도로 흘려보내는 프로그램. 매번 같은 조건에서 재기 위해.

> **여기서 실수를 한 번 했다 (발표 포인트).**
> 처음엔 "1초에 500건"을 초 시작마다 몰아서 보냈다. 평균은 맞지만 뒤쪽 메시지가 앞 묶음을 기다려 지연이 부풀려졌다. **시스템이 느린 게 아니라 내가 몰아 보낸 탓.**
> → 2ms마다 1건씩 균등하게 보내도록 고치자 측정값이 실제 성능을 반영하기 시작했다.
> **측정 도구 자체가 결과를 왜곡할 수 있다는 걸 확인하고 바로잡았다.**

부하 생성기는 실제 수집기가 쓰는 전송 코드를 그대로 재사용했다. 전송 설정이 운영과 달라지면 비교가 무의미해지므로.

### ③ 개선안마다 스위치

개선안 6개를 각각 껐다 켰다 할 수 있게 만들었다.

```java
private boolean instrumentRegistryFix = true;   // 버그 수정
private boolean instrumentCache      = false;   // 종목 재등록 캐시
private boolean prevCloseLocalCache  = false;   // 전일 종가 로컬 캐시
private boolean wsTaskExecutor       = false;   // 화면 전송 스레드풀
private boolean redisPipeline        = false;   // Redis 명령 묶기
private boolean storageIdempotency   = false;   // 저장 중복확인 묶기
```

- 원래 코드와 바꾼 코드를 **둘 다 남겨두고 실행할 때 `if`로 선택**
- 프로그램은 하나, 빌드도 한 번 → 비교 조건에서 코드 버전 차이라는 변수를 제거
- **하나씩만 켜면서** 측정 → 각 항목의 기여도를 분리

> 한꺼번에 다 켜면 "빨라졌다"는 알아도 "무엇 덕분인지"는 모른다.
> 실제로 이 방식 덕분에 6개 중 2개가 오히려 느려진다는 걸 잡아냈다.

## 5. 검증 결과 — 가설의 절반이 틀렸다

| 예측한 지점 | 실측 결과 |
| --- | --- |
| 배치 flush — "500건 모일 때까지 대기" | **그런 코드가 없음.** 평균 2~3건씩 즉시 처리 |
| Producer 전송 방식 — 동기 의심 | 이미 비동기. 의심한 코드가 없음 |
| Kafka 설정 (fetch 등) | 이미 최적값. 4개 중 3개는 이미 적용된 상태 |
| Redis 왕복 — "메시지당 3회" | **실제로는 5회.** 우리가 센 것보다 많았음 |
| 실시간과 저장의 분리 | **분리돼 있지 않았음** (7번 참조) |

**8개 중 4개가 사실이 아니거나 이미 해결된 상태였다.** 측정 없이 고쳤다면 시간만 버렸을 부분.

## 6. 진짜 원인 두 가지

두 문제 모두 **같은 파일 하나**에 있었다.
시세가 저장될 때마다 "이 종목이 종목 목록에 등록돼 있나?"를 확인·갱신하는 코드.

> 짚고 갈 것: **시세 데이터(가격)는 안 건드렸다.** 그건 계속 쌓는 게 당연하다.
> 문제는 **종목 목록**이었다 — 종목 50개짜리, 거의 안 바뀌는 표.

### 문제 ① — 50행 테이블에 49만 번 쓰기

같은 종목을 매번 다시 등록하고 있었다. 한 번 등록한 걸 기억하지 않아서.

```
테이블         새 정보 삽입   갱신(덮어쓰기)
instruments        50        495,652
```

새로운 정보는 딱 50건. 나머지 49만 번은 이미 있는 50줄에 "마지막 본 시각"만 고쳐 쓴 것.

정작 목적인 시세 저장(0.638ms)보다 이 목록 갱신(3.019ms)이 **4.7배 비쌌다.**

**개선:** 종목별 마지막 등록 시각을 메모리에 두고, 60초 지난 경우에만 갱신.

```
DB 쓰기 495,652회 → 100회   (50종목 × 2분)
```

### 문제 ② — 그 등록이 매번 오류를 내고 있었다

목록 갱신 명령이 **호출할 때마다 오류를 던지고 있었다.**

- "답장 없는 명령"용 함수로, "항상 답장이 오는 명령"을 보냈다 → 매번 오류
- 데이터는 정상적으로 들어감 (명령은 실행됨). 그 다음에 오류
- `catch`가 로그만 남기고 넘어가 아무도 몰랐음

```
2분 측정 1회에 발생한 오류: 84,937회
```

**개선:** 답장을 받아서 버리는 함수로 교체. 사실상 단어 하나 수정.

> **왜 문제없어 보였나:** 데이터는 들어갔으니 기능 장애가 아니었다.
> 다만 예외를 만들고(스택트레이스 기록) 로깅하는 CPU 비용이 매번 발생했다. **성능 낭비였고, 그래서 더 오래 발견되지 않았다.**

## 7. 실시간과 저장은 사실상 붙어 있었다

설계상 두 경로는 분리돼 있다. 그런데 **같은 프로그램 안에서 돌며 자원을 공유**했다.

| 분리됨 | 분리 안 됨 |
| --- | --- |
| 컨슈머 그룹 · 트랜잭션 · 스레드가 다름 | 같은 프로그램에서 실행 |
| 실시간 경로는 DB를 안 건드림 | CPU를 나눠 씀 |
| | **Redis로 나가는 연결을 공유** |

**저장 기능만 꺼보는 실험**으로 확인했다.

| | 저장 켬 | 저장 끔 |
| --- | --- | --- |
| Redis 조회 1회 | 0.494ms | 0.170ms |
| Redis 저장 1회 | 0.433ms | 0.136ms |
| 화면 도달 평균 | 231.75ms | 11.22ms |

**개별 Redis 명령이 3배 느려졌다** = 실시간 경로가 무언가를 기다렸다는 뜻.
문제 ①②로 무거워진 저장 경로가 CPU와 Redis 연결을 뺏어가고 있었다.

> **결론:** 결합은 구조적으로 존재한다. 다만 지금은 저장 경로를 가볍게 만드는 게 먼저.
> 프로세스 완전 분리는 부하가 더 커졌을 때의 선택지로 남겨둠 → **9월에 실제로 분리했다 (§13).**

## 9. 기각한 개선안 — 측정의 가치를 보여준 사례

설계 문서에 "Redis 왕복을 줄이려면 명령을 묶어 보내라"고 적어두고 구현했다.
**그런데 재보니 2.5배 느려졌다.**

| | 시간 |
| --- | --- |
| 명령 따로 2번 | 0.393ms |
| 묶어서 1번 | 0.964ms |

**원인:** 명령을 묶어 보내려면 전용 연결이 필요한데, 그 연결을 재사용하는 부품(연결 풀)이 프로젝트에 빠져 있었다. 그래서 묶을 때마다 **새 연결을 개통**했다.

```
평상시 연결 수                  3개
파이프라인 실행 후 누적 개통 횟수  366,493회
```

> **정확한 진단:** 명령 개수는 똑같다(SET 1 + PUBLISH 1). 차이는 Redis 쪽이 아니라
> **연결을 새로 만드는 비용**에 있었다. 왕복 2번을 아끼려다 왕복 여러 번짜리
> 연결 개통을 추가한 셈. 파이프라인이 나쁜 게 아니라 **전제조건(연결 풀)이 없었다.**

## 10. "느리면 무한히 쌓여서 터지지 않나?" — 부하 안정성 검증 (로컬)

개선 전에 수집→저장 지연이 수 분에 달했다. 자연스러운 의문:
**처리가 느리면 밀린 게 계속 쌓여 결국 시스템이 터져야 하는 것 아닌가?**
직접 부하를 걸어 확인했다. 답은 **아니다 — 터지지 않고, 정상 범위에선 유실도 없다.**

### 먼저, 왜 안 터지나

밀린 데이터는 **앱 메모리가 아니라 Kafka(디스크)에 쌓인다.** 소비자는 한 번에 정해진
양만 꺼내가므로, 밀린 물량이 아무리 커도 앱이 메모리 부족으로 죽지 않는다.
"터진다"가 아니라 "지연이 는다" 또는 "오래된 게 버려진다"가 실제 실패 방식이다.

### 실험 A — 용량 초과 부하 (정상 보관기간)

처리 용량을 넘는 6,000건/초로 12만 건을 투입.

| 시점 | 밀린 양(lag) |
| --- | --- |
| 부하 중 | 최대 약 30,000건까지 증가 (따라잡지 못함) |
| 부하 종료 | 수 초 만에 **0으로 배수** |

**12만 건 전송 = 12만 건 저장, 유실 0.**

→ 지연은 무한히 커지지 않는다. 큐가 특정 크기까지 늘었다가, 부하가 빠지거나
   처리 속도가 도착 속도 이상이 되면 배수된다.

### 실험 B — 밀린 게 보관기간을 넘긴 경우 (극단 상황 강제 재현)

밀린 3만 건을 삭제(= 보관기간 4시간 만료와 같은 효과)한 뒤 소비자를 재기동.

- 소비자가 "읽을 위치가 사라짐 → 최신으로 건너뜀" (로그로 확인)
- **3만 건 중 0건 저장 = 100% 유실. 단, 크래시는 없음.**

→ 무한히 쌓이는 대신, 보관기간을 넘기면 **크래시가 아니라 조용한 유실**로 상한이 걸린다.

> **9/20 실전 참고:** 이 실험이 예견한 시나리오가 오늘 실제로 벌어졌다 (§14).
> 다만 원인은 "느린 처리"가 아니라 "Redis 쓰기 자체가 아예 막힘"이었다 — 적체가 1,300만 건까지
> 쌓였지만 retention(4시간) 안에 원인을 찾아 복구해 유실 없이 넘겼다.

### 결론

> 관측했던 수 분의 지연은 **데이터 유실이 아니라 느린 처리로 생긴 대기 큐**였다
> (지연 ≪ 보관기간 4시간이라 유실 없음). 성능 개선으로 처리 용량을 약 4배 올려
> 이 지연을 12ms로 해소했다.

### 유실 조기 경보 모니터링

용량 초과가 4시간 이상 지속되면 실험 B처럼 조용히 유실될 수 있다. 크래시가 없어 더
위험하므로, 유실이 일어나기 **전에** 잡는 지표·경보를 붙였다. (9월에 실제 운영 배포까지 완료 — §12)

- **신규 지표**: 밀린 양(`consumer_lag`)과 **삭제 경계까지 남은 여유분**(`retention_margin`,
  0에 가까우면 유실 임박)을 상시 노출
- **3단계 경보**(Prometheus): 지연 시작(경고) → 지속 증가(심각) → 유실 임박(심각)
- **Discord 실시간 알림**: Alertmanager → Discord 웹훅 브릿지로 경보를 팀 채널에 즉시 전송,
  해소되면 "resolved"도 자동 전송

## 11. 후속 구현 — 발견한 기능 버그를 실제로 고침

분석과 코드 점검 과정에서 배치 파이프라인의 버그 두 가지를 찾아 고쳤다.
둘 다 "값이 화면/DB에 잘못 들어가던" 문제로, 겉보기엔 정상처럼 보여 오래 숨어 있었다.

### 11-1. 실시간 등락률이 항상 0

성능 분석 도중, 실시간 시세의 **등락률(전일 대비 %)이 항상 0으로 나오는** 기능 버그를 발견했다.

#### 원인

실시간 경로는 "현재가 vs 전일 종가"로 등락률을 계산한다. 그런데 **전일 종가를 채워주는 주체가 없었다.** 수동 API 하나로만 넣을 수 있었고, 운영 중엔 아무도 호출하지 않아 값이 늘 비어 있었다.

- 전일 종가 데이터 자체는 이미 있었다 — 일봉 집계 배치가 `symbol_daily_ohlcv`에 매일 종가를 쌓고 있었다.
- 그 값을 실시간 경로가 읽는 Redis로 **옮기는 배치가 없었을 뿐.**

#### 구현 (Spring Batch)

일봉 집계 직후 실행되는 **전일 종가 동기화 배치**를 추가했다.

```
일봉 집계 배치  →  [신규] 전일 종가 동기화 배치  →  지표 계산  →  검증
                        │
                        └→ symbol_daily_ohlcv 의 심볼별 최신 종가를
                           Redis(price:prev-close:{symbol})에 적재
```

- 매일 자동 실행 (기존 일일 배치 체인에 편입)
- 시연용 수동 실행 API 추가 (`POST /api/batch/prev-close-sync`)

#### 서버에서 실제 검증

실제 부하를 주고 배치 실행 전후를 비교했다.

| | 전일 종가 (Redis) | 실시간 등락률 |
| --- | --- | --- |
| **배치 실행 전** | 키 없음 | **항상 0%** |
| **배치 실행 후** | 10개 종목 적재됨 | **정상 계산** |

배치 실행 후 등락률이 계산식과 **정확히 일치**함을 확인했다.

| 종목 | 현재가 | 전일 종가 | 등락률 | 계산식 검증 |
| --- | --- | --- | --- | --- |
| SYM000 | 127.99 | 112.13 | **+14.15%** | +14.15% ✓ |
| SYM001 | 314.51 | 290.81 | **+8.15%** | +8.15% ✓ |
| SYM002 | 45.45 | 126.25 | **−64.00%** | −64.00% ✓ |
| SYM003 | 89.67 | 117.30 | **−23.55%** | −23.55% ✓ |

### 11-2. 기술적 지표가 틀린 값으로 계산됨

지표 계산 배치를 점검하다 **이력이 60일을 넘으면 모든 지표가 옛날 데이터로 고정 계산되는** 버그를 발견했다.

#### 원인

지표(이동평균·RSI·MACD 등)는 "최근 60일"의 종가로 계산해야 한다. 그런데 이력 조회가 **가장 오래된 60일**을 가져오고 있었다.

```
가져와야 할 것:  최근 60일  (61일째 ~ 65일째)   ← 오늘 기준 최신
실제 가져온 것:  오래된 60일 ( 1일째 ~ 60일째)   ← 아주 옛날 데이터
```

데이터가 60일을 넘는 순간부터, 지표 계산 창이 **맨 처음 60일에 영영 고정**된다. 값은 정상적으로 저장되므로 겉보기엔 문제가 없어 보인다.

#### 서버에서 실증

65일치(종가 1~65) 데이터를 넣고 마지막 날 지표를 계산했다.

| 지표 | 수정 전 | 수정 후 | 정답 |
| --- | --- | --- | --- |
| MA5 (최근 5일 평균) | **58** (56~60일) | **63** | 63 (61~65일) ✓ |
| MA20 | — | **55.5** | 55.5 ✓ |
| MA60 | — | **35.5** | 35.5 ✓ |

수정 후 모든 이동평균이 정답과 일치했다.

#### 같이 고친 것

- **견고성**: 한 종목의 계산이 실패하면 그날 전체 지표가 0건 저장되던 구조였다.
  종목별로 오류를 격리해, 한 종목이 실패해도 나머지는 정상 적재되도록 바꿨다.
- **지표 누락 자동 감지**: OHLCV는 있는데 지표가 안 들어간 종목을 찾아내는
  검증 단계를 추가했다. 지표를 일부러 지운 뒤 검증이 그 종목을 정확히 잡아내는 것까지 확인했다.

---

> 성능 분석에서 시작했지만, 그 과정에서 **화면·DB에 잘못 들어가던 기능 버그 두 개**를 찾아 고쳤다.
> 파이프라인을 구간별로 뜯어보고 배치를 직접 돌려보지 않았다면 드러나지 않았을 문제다.

## 12. 서버 실측 검증 (9/7) — "4,300"은 재현되지 않았다

목표: 이전 미팅에서 나온 "현재 처리 속도 = 초당 4,300건" 검증 + 실제 한계 지점 파악.

### 요약

| | Phase 1 (당시 배포본) | Phase 2 (최신 코드+12파티션) |
| --- | --- | --- |
| `market.normalized` 파티션 | 6 | 12 |
| realtime 컨슈머 스레드 활성 | 6 / 12 | **12 / 12** |
| **realtime 지속 처리량** | **~2,800 msg/s** | **~3,000 msg/s** |
| **포화 시작(적체 급증)** | ~3,000–3,500 | ~4,000–4,300 |

| 병목 | 앱 CPU 4코어 고정 + 6파티션 | **Redis 커넥션 1개** (§9에서 기각했던 그 파이프라인의 전제조건) |

**"4,300"은 이 서버에서 재현되지 않았다.** 그 숫자는 최적화 코드(로컬, 12파티션, 작은 DB) 기준이며
서버에는 배포된 적이 없었다. 서버 실측 지속 처리량은 **~2,800–3,000 msg/s (realtime 경로)**.

> 로컬 결론을 그대로 믿지 않고 실제 배포 환경에서 재검증한 것 자체가 이번 단계의 핵심이다.
> §부록 A에서 이미 "절대값은 참고용, 서버 바뀌면 달라진다"고 명시해뒀던 그대로 확인된 셈.

### "몇 건 보내면 터지나?" → 여기서도 안 터진다

- 8,000 msg/s로 2분(96만 건) 투입해도 앱 크래시·OOM·유실 **0**.
- 초과분은 Kafka 디스크에 lag로 쌓였다가 부하가 빠지면 배수된다.
  - Phase 1: 3,000→lag 1만, 4,000→10만, 6,000→28만, 8,000→44만 (선형 증가)
  - 부하 종료 후 배수: 3,500→5초, 5,000→46초, 8,000→100초+ (backlog 클수록 오래)
- retention(4h) 넘게 초과가 지속되면 그때 **조용한 유실**(크래시 아님). §10 실험 B와 같은 방식.

### Phase 1 상세 (6 파티션, 당시 배포본)

| rate | 소비 rt | 소비 st | peak lag(rt) | 배수 | 판정 |
| ---: | ---: | ---: | ---: | ---: | :--- |
| 2,500 | 2,326 | 2,326 | 0 | 즉시 | 따라감 |
| 2,800 | 2,646 | 2,646 | 98 | 즉시 | 따라감 |
| 3,000 | 2,769 | 2,769 | **10,440** | 즉시 | 경계 |
| 3,500 | 2,794 | 3,134 | 48,678 | 5초 | 포화 |
| 5,000 | 2,867 | 3,938 | 188,878 | 46초 | 포화 |
| 8,000 | 2,815 | 3,841 | 435,695 | 100초+ | 포화 |

부하 3,000+ 구간: 앱 CPU 400–417%(4코어)에 고정, load1 13–16.
rate를 8,000까지 올려도 realtime 소비는 ~2,850에 고정 = 하드 실링.

### Phase 2 상세 (12 파티션, 최신 코드)

| rate | 소비 rt | 소비 st | 배수 | 판정 |
| ---: | ---: | ---: | ---: | :--- |
| 3,000 | 2,791 | 2,761 | 0초 | 따라감 (Phase 1은 lag 1만) |
| 4,000 | 3,235 | 3,551 | 10초 | 경계 (Phase 1은 lag 10만) |
| 4,300 | 3,368 | 3,851 | 15초 | 포화 |
| 6,000 | 3,258 | 4,512 | 57초 | 포화 |

- 12 스레드 전부 활성 + 최적화로 rate 2,000에서 앱 CPU 240–340%(Phase 1은 337%) — 건당 CPU 감소.
- realtime 소비는 여전히 ~3,100–3,400에서 평평 → **Redis 커넥션 1개가 유일한 하드 실링**.
  12 컨슈머 스레드가 GET/SET/PUBLISH를 단일 Lettuce 연결로 직렬화.
- 당시 Redis `maxmemory 256MB`에 상시 붙어 초당 ~2,000–2,600 키 축출, 멱등성 키가 TTL 전에
  축출돼 사실상 무력화됨을 확인 → 이후 `2GB`로 상향 조치 완료.

### 이후 적용한 개선 (§9 "기각한 개선안"의 후속)

1. `commons-pool2` 의존성 추가 → Lettuce 커넥션 풀 활성화 → 12스레드가 Redis I/O를 병렬로.
2. `STOCKFLOW_OPT_REDIS_PIPELINE=true` → 왕복 3회→1회로 묶기 (이제 전제조건이 있으니 §9의 실패가 재발하지 않음).
3. Redis `maxmemory` 256MB → 2GB 상향.
4. 실시간/저장 프로세스 분리 옵션 추가 (`--profile split`) — CPU 경합이 심해지면 즉시 분리 가능.

- 코드에는 이미 전 종목 구독 로직(`"*"` 와일드카드)이 있었지만, 서버엔 **컨테이너 자체가
  떠 있지 않았다** (선택적 profile로 게이팅 + API 키 미설정).
- API 키를 발급받아 연동을 시도하자 **`405 symbol limit exceeded`** 에러 발생 —
  Alpaca 무료 마켓데이터 플랜은 동시 구독 가능한 종목 수에 상한이 있음을 실측으로 확인.
- 원인을 더 파보니, 구독 요청이 체결(trades)과 호가(quotes)를 **동시에** 요청하고 있었는데
  호가는 수신해도 애초에 처리하지 않고 버리는 코드였다 — **안 쓰는 구독이 한도를 절반 낭비**하고 있었음.
- 호가 구독을 제거하고, 무료 플랜 한도 내에서 시가총액 상위 30종목(AAPL·MSFT·GOOGL·NVDA 등)으로
  범위를 맞춰 재시도.

**서버 실측 (수정 후 로그):**
```
✅ Alpaca 인증 성공
✅ 구독 완료 | 체결: 30개 종목 | 호가: 0개 종목
```

> 참고: 검증 시점이 일요일이라 미국 증시 휴장 — 연결·구독은 정상이지만 실제 체결 데이터는
> 월요일 정규장부터 들어온다 (코인은 24시간 시장이라 즉시 확인 가능했음).

### 13-3. UI 라이트 테마 리디자인

다크 네온 개발자 대시보드 → 실제 증권사(MTS) 스타일 라이트 테마로 4개 화면(대시보드/실시간시세/
종목&차트/백테스팅) 전면 개편. 한국 증권사 관례(상승=빨강/하락=파랑) 반영, Pretendard 폰트 적용.
API 호출·WebSocket 로직은 변경 없이 시각적 요소만 교체 — 헤드리스 브라우저로 4페이지 렌더링과

## 14. 인시던트 — Redis가 탈취되어 있었다

기능 배포 직후 "실제로 데이터가 잘 들어오는지" 확인하다가 발견한 운영 인시던트. 실시간 서비스를
가정하면 반드시 겪게 되는 종류의 문제라 별도 섹션으로 남긴다.

### 증상

배포 후 Discord로 컨슈머 적체(lag) 경보가 반복 수신됨 (§10에서 만든 조기 경보가 실제로 작동한 사례).

### 1차 진단 (틀림)

로그에 `RedisPipelineException: Pipeline contained one or more invalid commands`가 대량으로 찍혀
있어, 저장 경로 멱등성 체크를 Redis 파이프라인으로 묶는 최적화 옵션
(`STOCKFLOW_OPT_STORAGE_IDEMPOTENCY_PIPELINE`)의 버그로 추정하고 껐다. **재배포해도 증상 동일.**

### 재진단 — 진짜 원인

같은 에러의 전체 스택 트레이스를 다시 훑자 근본 원인이 드러났다.

```
Caused by: io.lettuce.core.RedisReadOnlyException:
    READONLY You can't write against a read only replica.
```

Redis에 직접 `INFO replication`을 조회:

```
role:slave
master_host:109.244.159.27
master_port:20718
master_link_status:down
```

**이 프로젝트 설정 어디에도 `replicaof`는 없다.** Redis 포트(6379)가 비밀번호 없이 외부에
노출된 상태였고, 자동화된 스캐너/봇이 `SLAVEOF <임의 IP> <포트>` 명령을 주입해 Redis를
"읽기 전용 replica"로 만들어버린 것으로 판단된다 — 인증 없는 Redis를 노리는 잘 알려진 공격 패턴.
다행히 `master_repl_offset:0`, `link_status:down`으로, 공격자 쪽으로부터 실제 데이터(RDB) 동기화는
이뤄지지 않은 것으로 보인다.

이게 모든 쓰기를 실패시켜 컨슈머가 완전히 멈췄다 (15초간 처리 오프셋 0 증가로 확인) → 적체가
realtime 1,350만 건, storage 1,140만 건까지 쌓였다.

### 복구

`REPLICAOF NO ONE`으로 Redis를 원래 상태(standalone master)로 되돌림. 즉시 쓰기가 재개되며
컨슈머가 다시 진행되기 시작했고(실시간 그룹 ~32,000 msg/s, 저장 그룹 ~7,900 msg/s로 드레인),
Discord 경보도 자동으로 resolved 처리됨.

### 남은 과제 (미조치 — 중요)

증상은 복구했지만 **원인(인증 없이 노출된 Redis 포트)은 아직 그대로**다. 다음 조치가 필요하다.

- Redis에 `requirepass` 설정
- `docker-compose.yml`의 `6379:6379` 포트 바인딩을 내부 전용으로 제한 (또는 방화벽 차단)

> **배운 점:** "적체 경보 = 처리량 부족"이라는 첫 가설에 갇혀서 파이프라인 옵션을 껐다 켰다 했는데,
> 증상만 같았지 원인이 아니었다. 최종 스택 트레이스의 `Caused by`까지 끝까지 읽고서야 진짜 원인이
> 나왔다 — §5 "가설의 절반이 틀렸다"와 같은 교훈이 운영 인시던트에서도 그대로 반복됐다.

## 16. 배운 점

**예측한 지점 6개 → 맞은 것 3개, 틀린 것 2개, 예측 못 한 것 1개(가장 큰 효과)**

- 병목은 직관과 다른 곳에 있었다. 가장 큰 원인은 예측 목록에 없었다.
- 일반적으로 옳은 최적화(명령 묶기)가 특정 환경(연결 풀 없음)에서는 틀릴 수 있다 — 그리고 그
  전제조건만 채우면(§12) 원래 판단이 맞았다는 것도 확인했다.
- **로컬 결론을 서버에서 재검증한 게 옳은 선택이었다.** "4,300"을 그대로 믿었다면 실제 배포
  환경의 진짜 한계(~2,800~3,000)를 몰랐을 것이다.
- **운영 인시던트도 같은 태도로 접근해야 한다.** 처음 떠오른 가설(파이프라인 버그)에 만족하지 않고
  전체 스택 트레이스를 끝까지 읽은 덕분에 진짜 원인(Redis 탈취)을 찾았다.
- 측정을 먼저 한 게 옳은 선택이었다. 예측만 믿었다면 틀린 개선안을 적용해 시스템을 더 느리게
  만들고, 정작 진짜 원인은 놓쳤을 것.

## 부록 B. 예상 질문과 답

**Q. 실시간 데이터를 계속 저장하는 건 당연한 것 아닌가?**
시세 저장은 그대로 뒀다. 문제는 시세가 아니라 종목 마스터 목록이었다. 50행 표에 49만 번 썼는데 새 정보는 50건뿐, 나머지는 같은 내용 덮어쓰기였다.

**Q. 오류가 8만 번 났는데 왜 문제가 없었나?**
데이터는 정상적으로 들어갔다. 명령 실행 후 응답 처리 단계에서 난 오류라서. 다만 예외 생성·로깅 비용이 매번 발생했다. 기능 장애가 아니라 성능 낭비였고, 그래서 더 오래 안 보였다.

**Q. 화면까지 잰 건가, Redis 발행까지 잰 건가?**
Redis에 발행한 뒤 같은 서버가 구독으로 되받아 화면 전송 계층에 넘기는 지점까지 쟀다. 단, 브라우저가 실제 받는 시점은 아니다.

**Q. 개선 판단은 어느 수치로 했나?**
구간별 시간과 처리 횟수를 주 근거로 썼다. 특히 처리 횟수(49만→100회)는 환경과 무관해 가장 확실한 근거.

**Q. 파이프라인은 결국 못 쓰는 건가?**
아니다. §9에서 "연결 풀이 먼저"라고 결론 내렸고, §12에서 실제로 연결 풀(commons-pool2)을 추가한 뒤 파이프라인을 다시 켰다. 지금은 정상 적용되어 운영 중이다.

**Q. "4,300건"은 왜 틀렸나?**
그 수치는 로컬(맥 Docker Desktop, 12파티션, 작은 DB) 기준이었고 서버에는 그 구성이 배포된 적이 없었다. 서버는 그 시점에 6파티션·구코드였고, 실측 상한은 ~2,800건/초였다. 절대값은 환경마다 다르다는 부록 A의 원칙 그대로다.

**Q. 종목이 746개로 늘면 처리량에 문제없나?**
메모리엔 종목 수만큼만 저장되므로 구조적 문제는 없다. 다만 종목이 늘면 틱 유입량 자체가 늘어날 수 있어 §12에서 확인한 처리 상한(~2,800~3,000/s)에 더 가까워질 수 있다 — §15에서 최신 상태로 재검증 중인 이유다.

**Q. Redis가 왜 뚫렸나? 이게 이 프로젝트만의 문제인가?**
인증(비밀번호) 없이 Redis 포트를 외부에 노출하면 흔히 겪는 문제다 — 자동화된 스캐너가 인터넷을 훑다가 열린 Redis를 찾아 복제(replica) 명령을 주입하는 알려진 공격 패턴. 프로젝트 코드의 버그가 아니라 배포 설정(포트 노출 + 무인증)의 문제였고, 재발 방지 조치(비밀번호 설정, 포트 제한)가 남아있다.

**Q. 그 인시던트 때 데이터가 유실됐나?**
아니다. 적체가 1,300만 건까지 쌓였지만 Kafka 보관기간(4시간) 안에 원인을 찾아 복구했다. §10 실험 A와 같은 케이스 — 지연은 있었지만 유실은 없었다.

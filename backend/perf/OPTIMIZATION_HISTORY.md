# StockFlow 처리량 최적화 이력

> 서버 한 대(8코어·15GB·HDD 1개)가 초당 몇 건의 체결을 처리하는가, 그리고 무엇이 그 숫자를 올렸는가.
> 측정: 2026-09-28 ~ 10-05. 원본 결과: 서버 `~/perf-rev/backend/perf/results/`.

## 1. 한눈에 — 3단계로 6배

```
처리 상한(건/초)   0        4,000      8,000      12,000
7/8  출발점        ██ 2,000
9/21 1단계 후      ██████ 6,000                         (×3)
10/5 2단계 후      ████████████ 12,000                  (×2)
```

| 단계 | 그때의 병목 | 한 일 | 처리 상한 |
|---|---|---|---:|
| **출발점** (7/8, `1f814a5`) | 실시간 경로가 Redis 연결 1개를 12개 스레드가 나눠 씀 + DEBUG 로그 폭주 | — | **약 2,000** |
| **1단계** (→ 9/21, `30c7a5a`) | 위와 같음 | Redis 연결 풀, 명령 묶기(파이프라인), 화면 전송 스레드풀, 로그 INFO, 종목 등록 캐시 등 | **약 6,000** (×3) |
| **2단계** (→ 10/5, `fae1466`) | 저장 경로: 작은 배치, 행마다 INSERT, 풀 경합, Redis 메모리 부족 | 저장 경로 설정 6개를 묶어서 변경 | **약 12,000** (×2) |
| 다음 한계 | 앱·DB·Redis 가 CPU 6코어를 모두 사용 | 코드만으로는 15,000~18,000 정도가 한계로 추정 | — |

**측정 방식**: 같은 서버·같은 부하(미국 주식 시뮬레이터)·같은 시간대에, 앱 이미지만 그 시점 코드로 바꿔 끼워 쟀다. "처리 상한" = 밀린 양(lag)이 늘지 않고 따라간 최대 초당 건수.

## 2. 단계별로 무엇을 바꿨고, 각각 얼마나 기여했나

각 단계 안의 변경은 **하나씩 켜고 끄며** 따로 쟀다(9/28~10/5, 합성 부하·가짜 50종목, 90초). 숫자는 소비량(건/초)이고, 90초 한 번 측정이라 **±10% 안은 노이즈**로 본다.

### 1단계: 출발점 → 9/21 (2,000 → 6,000)

**병목**: 실시간 처리 스레드 12개가 Redis 연결 1개를 줄 서서 썼고, 메시지마다 DEBUG 로그를 찍었다.

| 변경 | 측정 방법 | 결과 | 기여 |
|---|---|---|---|
| **Redis 연결 풀** | 도입 직전·직후 코드 비교 (rate 7,000) | 실시간 523 → 2,453 | **4.7배** (가장 큼) |
| **로그 DEBUG → INFO** | 연결 풀 코드 → 로그 변경까지 들어간 코드 (그 사이 다른 작은 수정 포함) | 2,453 → 6,176 | **+150%** |
| **화면 전송 스레드풀** | 끄고 재기 | 6,176 → 1,684 | 없으면 **−73%** |
| **Redis 명령 묶기** (최신가 저장+발행 1왕복) | 끄고 재기 | 6,176 → 5,000 | 없으면 **−19%** |
| 종목 등록 캐시, 전일 종가 캐시 | 끄고 재기 | 6,300, 6,238 | 노이즈 (처리량 아닌 DB 부담·정확성 개선) |
| 재시도 버그 수정, Redis KEYS→SCAN | 직전·직후 코드 비교 | 5,833, 5,943 | 노이즈 (장애·대량 키 상황에서만 드러남) |

→ 실시간 경로는 풀렸지만, 이번엔 **저장 경로가 6,600에서 멈췄다**(아래 §3 표의 9/21 열).

### 2단계: 9/21 → 10/5 (6,000 → 12,000)

**병목**: 저장 경로가 한 번에 조금씩 가져와(배치 100), DB 에 행마다 INSERT 를 보내고, Redis 연결을 두고 스레드가 경쟁했으며, 중복 방지 키가 24시간 쌓여 Redis 메모리(2GB)가 가득 찼다.

| 변경 | 단독으로 켰을 때 저장 소비 (rate 8,000, 기준 6,329) | 기여 |
|---|---|---|
| **DB 묶음 INSERT** (`reWriteBatchedInserts`) | 7,129 | **+13%** |
| **중복 확인 묶기 + Redis 연결 48개** | 6,990 | **+10%** (연결 16개일 땐 −59% → 원인은 연결 부족) |
| **저장 배치 100 → 500건** | 6,923 | **+9%** |
| DB 연결 24개 | 6,432 | 노이즈 |
| Redis 연결 48개만 | 6,148 | 노이즈 |
| 중복 방지 키 유효시간 24시간 → 10분 | (Redis 메모리 부족 해소용) | 노이즈 |
| **위 6개를 전부 함께** (rate 10,000, 4회 반복) | 평균 3,662 → **7,260** | **약 2배** |

→ **하나씩은 ±10% 안팎인데, 합치면 2배.** 병목이 한 곳이 아니라 여러 곳에 겹쳐 있었기 때문이다. 4회 반복에서 조합의 최저값(5,887)이 기준의 최고값(4,553)보다 높아 노이즈가 아니다.

이 묶음을 코드 기본값으로 반영한 `fae1466` 을 env 없이 띄워도 같은 효과가 났다(같은 시간대 교차 측정: 옛 코드 6,256·5,820 → 새 코드 **8,982**).

### 해보고 버린 것

| 시도 | 결과 | 이유 |
|---|---|---|
| 컨슈머 스레드 12 → 8 | 저장 −17% | 오히려 느려짐 |
| JVM 힙 1.5GB 고정 | 저장 −21% | 오히려 느려짐 |
| DB `synchronous_commit=off` | +6% | 장애 시 데이터 유실 위험 대비 이득이 작음 |
| 실시간 배치 소비, 지연 측정 샘플링, Redis 전송 방식 변경 | 노이즈 | 코드만 남기고 기본은 꺼 둠 |
| 중복 인덱스 삭제, 파티션 키 분산 | 미시도 | 라이브 DB 위험 / 종목별 순서가 깨짐 |

**한계**: 90초 단일 표본(±10%), 공용 서버라 시간대에 따라 절대값이 최대 2배 흔들림 → 같은 시간대에 이어서 잰 상대 비교만 근거로 쓴다. §2 의 개별 기여는 예전 합성 부하로 잰 값이라 §3 과 절대값을 직접 비교하지 않는다.

## 4. 분석(예측) 서비스 용량 예약

- 분석 컨테이너 = 코어 6–7 · CPU 가중치 2배 · 메모리 3GB, 나머지 컨테이너 = 코어 0–5 (`backend/infra/reserve-analysis-capacity.sh`, 배포 때 자동 재적용).
- 파이프라인을 4,000 → 20,000건/초로 올리는 동안 예측 API 는 **전부 성공, 응답 중앙값 0.7~1.1초**, 최대 7.8초(첫 학습 포함).
- 모델 캐시가 없는 종목의 첫 호출만 학습 때문에 10~15초, 이후는 약 1초.

## 5. 반영 상태

- 2단계 코드(#47)는 10/5 에 main 병합·서버 배포 완료(롤백용 이미지 `stockflow-app:pre-deploy-20261005`). 배포 후 Redis 메모리 2.0GB(가득) → 1.3GB.
- 서버 `.env` 의 옛 고정값(`STOCKFLOW_OPT_STORAGE_IDEMPOTENCY_PIPELINE=false`)은 새 기본값을 덮어써서 제거했다(백업 `.env.bak.20261005`).
- 되돌리기: TTL·저장 배치는 `.env` 에 옛 값(`STOCKFLOW_IDEMPOTENCY_TTL_SECONDS=86400`, `KAFKA_STORAGE_MAX_POLL_RECORDS=100` 등). 연결 풀·JDBC 옵션은 `application.yml` 고정값이라 compose `environment:` 에 추가하거나 이전 이미지로 복귀 — [RUNBOOK.md §3](../../RUNBOOK.md#3-스택-조작).
- 모든 수치는 모의 부하·서버 1대 기준이다. 미국 전 종목 실제 체결량으로 검증한 것은 아니다.

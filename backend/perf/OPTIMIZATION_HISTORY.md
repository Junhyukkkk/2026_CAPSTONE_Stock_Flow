# StockFlow 처리량 최적화 이력

> 서버 한 대(8코어·15GB·HDD 1개)가 초당 몇 건의 체결을 처리하는가, 그리고 무엇이 그 숫자를 올렸는가.
> 측정: 2026-10-05 ~ 06, **전부 미국 주식 시뮬레이터 부하**. 원본 결과: 서버 `~/capstone/backend/perf/results/`.

## 1. 한눈에 — 3단계로 6배

```
처리 상한(건/초)   0        4,000      8,000      12,000
7/8  출발점        ██ 2,000
9/21 1단계 후      ██████ 6,000                         (×3)
10/5 2단계 후      ████████████ 12,000                  (×2)
```

| 단계 | 그때의 병목 | 한 일 | 처리 상한 |
|---|---|---|---:|
| **출발점** (7/8, `1f814a5`) | 실시간 경로가 Redis 연결 1개를 12개 스레드가 나눠 씀 + DEBUG 로그 폭주 | — | **약 2,000** |
| **1단계** (→ 9/21, `30c7a5a`) | 위와 같음 | Redis 연결 풀, 명령 묶기(파이프라인), 화면 전송 스레드풀, 로그 INFO, 종목 등록 캐시 등 | **약 6,000** (×3) |
| **2단계** (→ 10/5, `fae1466`) | 저장 경로: 작은 배치, 행마다 INSERT, 풀 경합, Redis 메모리 부족 | 저장 경로 설정 6개를 묶어서 변경 | **약 12,000** (×2) |
| 다음 한계 | 앱·DB·Redis 가 CPU 6코어를 모두 사용 | 코드만으로는 15,000~18,000 정도가 한계로 추정 | — |

**측정 방식**: 같은 서버·같은 부하·같은 시간대에, 앱 이미지(또는 설정)만 바꿔 쟀다. "처리 상한" = 밀린 양(lag)이 늘지 않고 따라간 최대 초당 건수.

## 2. 무엇이 얼마나 기여했나 (하나씩 켜고 끈 측정)

**조건(공통)**: 미국 주식 시뮬레이터 부하(105종목, 실제 종목·가격대·체결 흐름), 파티션 12, 앱·부하기 코어 0–5, 한 번에 90초 유지, 매 런 lag 0 에서 시작.
**읽는 법**: `실시간 / 저장` = 그 rate 동안 평균 소비량(건/초). 90초 평균이라 램프업 때문에 전송량의 약 88~90%로 보이면 "따라가는 중"이다. **같은 설정을 반복하면 ±5~10% 흔들리므로 그 안의 차이는 노이즈**로 본다.

### 2-1. 1단계 — 코드 시점별 (rate 6,000)

| 코드 | 무엇이 바뀐 시점 | 실시간 / 저장 | 판정 |
|---|---|---|---|
| `1f814a5` 7/8 | 출발점 | 2,908 / 3,860 | 포화 |
| `7cad4fe` 9/7 | 연결 풀 **직전** (Redis 파이프라인은 켜진 상태) | **449** / 5,289 | 포화 |
| `9771126` 9/7 | **Redis 연결 풀 도입** | **4,017** / 4,314 | 포화 |
| `97db656` 9/20 | + 로그 DEBUG→INFO 등 | **5,328** / 5,328 | 경계(밀림 해소) |
| `30c7a5a` 9/21 | 1단계 완료 | 4,844 · 5,302 (2회) / 4,534 · 5,302 | 경계 |

- **연결 풀**: 실시간 449 → 4,017 (**약 9배**). 풀 없이 파이프라인을 켜면 호출마다 연결을 새로 열어 급락하는데(7월 로컬 측정에서 확인한 현상과 같은 원인으로 보인다), 풀을 넣자 풀렸다.
- **로그 레벨**: 4,017 → 5,328 (**+33%**).
- 이 단계가 끝나면 실시간은 풀리고 **저장이 6,600 근처에서 막힌다** → 2단계로.

### 2-2. 1단계에서 넣은 항목을 하나씩 끄기 (`30c7a5a` 이미지, rate 12,000)

| 끈 것 | 실시간 | 저장 | 판정 | 기준 대비(실시간) |
|---|---:|---:|---|---|
| (기준: 전부 켬) | 10,462 | 6,967 | 경계 | — |
| **화면 전송 스레드풀** | 8,696 | 5,186 | 포화 | **−17%** |
| **전일 종가 로컬 캐시** | 9,171 | 6,971 | 포화(밀림 22만) | **−12%** |
| Redis 파이프라인(저장+발행 1왕복) | 9,774 | 7,517 | 경계 | −7% (노이즈 경계) |
| 종목 등록 캐시 | 10,653 | 6,960 | 경계 | +2% (영향 없음) |

- **rate 6,000(여유 있는 부하)에서는 네 항목 모두 차이가 없다**(기준 5,302, 끈 값 5,301~5,444). 항목은 **한계 가까이 갈 때** 효과가 드러난다.
- 예전(9/28, 합성 부하·가짜 50종목)에는 스레드풀 −73%, 파이프라인 −19% 로 더 컸다. 부하 모양이 달라 효과 크기가 다르게 나온다 — 시뮬레이터가 더 실제에 가까우므로 이 표를 기준으로 쓴다.
- 종목 등록 캐시는 처리량이 아니라 **DB 쓰기 49만 회 → 100회**(7월 로컬)로 DB 부담을 줄이는 항목이다.

### 2-3. 2단계 — 저장 경로 설정 6개 (`fae1466` 이미지, rate 12,000)

바꾼 설정 6개: ① 저장 배치 100→500건(`KAFKA_STORAGE_*`) ② DB 묶음 INSERT(`reWriteBatchedInserts`) ③ Redis 연결 16→48 ④ 멱등성 확인 묶기(파이프라인) ⑤ DB 연결 10→24 ⑥ 중복 방지 키 유효시간 24h→10분.

**(가) 최신 설정에서 하나씩 옛 값으로 되돌리기** — 기준 저장 소비 **약 9,900** (9,708 · 10,127, 두 번 측정)

| 되돌린 것 | 저장 | 기준 대비 | 실시간 |
|---|---:|---|---:|
| Redis 연결 48 → 16 | 8,327 | **−16%** | 9,391 (포화) |
| DB 묶음 INSERT 끔 | 8,662 | **−13%** | 10,768 |
| 저장 배치 500 → 100 | 8,788 | **−11%** | 10,762 |
| 키 유효시간 10분 → 24시간 | 8,989 | −9% | 9,511 |
| 멱등성 확인 묶기 끔 | 9,832 | −1% | 10,195 |
| DB 연결 24 → 10 | 9,961 | 0% | 10,457 |
| **6개 전부 옛 값** | **7,041** | **−29%** | 10,637 |

**(나) 옛 설정(전부 옛 값)에서 하나씩 새 값으로 올리기** — 기준 저장 소비 **약 6,900** (6,846 · 7,041)

| 올린 것 | 저장 | 기준 대비 |
|---|---:|---|
| **DB 묶음 INSERT** | 8,402 | **+23%** |
| **저장 배치 100 → 500** | 8,005 | **+17%** |
| **멱등성 확인 묶기** | 7,756 | **+13%** |
| Redis 연결 16 → 48 | 7,139 | +4% |
| DB 연결 10 → 24 | 7,030 | +3% |
| 키 유효시간 10분 | 6,440 | −6% (노이즈) |

**읽는 법**
- 전부 옛 값(약 6,900~7,040)이 9/21 코드의 한계(6,600)와 맞는다 → 이 6개가 9/21→10/5 개선의 전부다.
- **DB 묶음 INSERT 와 저장 배치**는 두 방향 모두 크다(−13%/+23%, −11%/+17%). Redis 연결 48 과 멱등성 묶기는 방향에 따라 크기가 다르다(−16%/+4%, −1%/+13%) — 서로 맞물려 효과가 나기 때문으로 보인다. DB 연결·키 유효시간은 처리량에 거의 영향이 없다.
- 각각은 10~20% 인데 **합치면 +43%**(6,900 → 9,900). 병목이 여러 곳에 겹쳐서 하나만 풀면 다음 병목이 막기 때문이다(합이 단순 합산보다 작다).
- 키 유효시간 10분은 처리량이 아니라 **Redis 메모리**를 위한 설정이다(배포 후 2.0GB 가득 → 1.3GB).

### 2-4. 해보고 버린 것 (합성 부하로 잼, 이번 재측정 대상 아님)

| 시도 | 결과 | 이유 |
|---|---|---|
| 컨슈머 스레드 12 → 8 | 저장 −17% | 오히려 느려짐 |
| JVM 힙 1.5GB 고정 | 저장 −21% | 오히려 느려짐 |
| DB `synchronous_commit=off` | +6% | 장애 시 유실 위험 대비 이득이 작음 |
| 실시간 배치 소비, 지연 측정 샘플링, Redis 전송 방식 변경 | 노이즈 | 코드만 남기고 기본은 꺼 둠 |
| 중복 인덱스 삭제, 파티션 키 분산 | 미시도 | 라이브 DB 위험 / 종목별 순서가 깨짐 |

## 4. 분석(예측) 서비스 용량 예약

- 분석 컨테이너 = 코어 6–7 · CPU 가중치 2배 · 메모리 3GB, 나머지 컨테이너 = 코어 0–5 (`backend/infra/reserve-analysis-capacity.sh`, 배포 때 자동 재적용).
- 파이프라인을 4,000 → 20,000건/초로 올리는 동안 예측 API 는 **전부 성공, 응답 중앙값 0.7~1.1초**, 최대 7.8초(첫 학습 포함).
- 모델 캐시가 없는 종목의 첫 호출만 학습 때문에 10~15초, 이후는 약 1초.

## 6. 주의

- **측정 중에는 화면이 안 열리고 수집이 멈춘다.** 앱 컨테이너를 테스트 이미지로 계속 갈아 끼우고, 코인·시뮬레이터·Alpaca 수집을 멈춘다. 끝나면 자동 복구된다(복구 후 화면·수집 확인할 것).
- **측정 중에 main 에 병합하지 말 것.** 병합하면 배포(CD)가 같은 컨테이너 이름을 건드려, 이번 재측정에서 서비스가 9/7 옛 이미지로 올라온 채 남았다(수동으로 복구). 그 시간대(CD 이미지 빌드와 겹친 1회)의 값은 버리고 다시 쟀다.
- 측정이 만든 `source=SIMLOAD` 행은 끝난 뒤 지운다 → [RUNBOOK.md §8](../../RUNBOOK.md#8-시뮬레이터--테스트-데이터). 옛 이미지가 만든 멱등성 키는 24시간 유효라 Redis 메모리를 잠시 채운다.
- 서버 시계는 NTP 미동기라 실제와 다르고, 측정 중에도 한 번 크게 바뀐 것이 관찰됐다. 로그 시각은 참고용으로만 본다.
- 모든 수치는 모의 부하(105종목)·서버 1대 기준이다. 미국 전 종목 실제 체결량으로 검증한 것은 아니다.

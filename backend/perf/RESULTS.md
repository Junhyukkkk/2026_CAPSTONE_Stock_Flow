# 서버 처리량(TPS) 측정 결과 — 2026-09-07

학교 서버(`itm3`, 114.71.51.41, 8코어/15GB)에서 `tps-sweep.sh` 로 실측.
목표: 8/5 미팅의 "현재 처리 속도 = 초당 4,300건" 검증 + 한계 지점 파악.

## 요약

| | Phase 1 (현 배포) | Phase 2 (최신+12파티션) |
| --- | --- | --- |
| 코드 | 서버 배포본 `1f814a5` (성능개선 이전) | `main` `404fe49` |
| `market.normalized` 파티션 | 6 | 12 |
| realtime 컨슈머 스레드 활성 | **6 / 12** | **12 / 12** |
| **realtime 지속 처리량** | **~2,800 msg/s** | **~3,000 msg/s** |
| **포화 시작(적체 급증)** | ~3,000–3,500 | ~4,000–4,300 |
| realtime 과부하 시 소비율(고정값) | ~2,850 | ~3,300 |
| storage(DB) 처리량 | ~4,000 | ~4,700 (계속 상승) |
| 병목 | 앱 CPU 4코어 고정 + 6파티션 + Redis 커넥션 1개 | **Redis 커넥션 1개** (`commons-pool2` 없음) |

**"4,300"은 이 서버에서 재현되지 않았다.** 그 숫자는 최적화 코드(로컬, 12파티션, 작은 DB) 기준이며
서버에는 배포된 적이 없었다. 서버 실측 지속 처리량은 **~2,800–3,000 msg/s (realtime 경로)**.

## "몇 건 보내면 터지나?" → 안 터진다

- 8,000 msg/s 로 2분(96만 건) 투입해도 앱 크래시·OOM·유실 **0**.
- 초과분은 Kafka 디스크에 lag 로 쌓였다가 부하가 빠지면 배수된다.
  - Phase 1: 3,000→lag 1만, 4,000→10만, 6,000→28만, 8,000→44만 (선형 증가)
  - 부하 종료 후 배수: 3,500→5초, 5,000→46초, 8,000→100초+ (backlog 클수록 오래)
- retention(4h) 넘게 초과가 지속되면 그때 **조용한 유실**(크래시 아님). `retention-cliff-test.sh` 로 재현 가능.

rate 를 8,000까지 올려도 realtime 소비는 ~2,850에 고정 = 하드 실링.

## Phase 2 상세 (12 파티션, 최신 코드)

| rate | 소비 rt | 소비 st | 배수 | 판정 |
| ---: | ---: | ---: | ---: | :--- |
| 3,000 | 2,791 | 2,761 | 0초 | 따라감 (Phase 1은 lag 1만) |
| 4,000 | 3,235 | 3,551 | 10초 | 경계 (Phase 1은 lag 10만) |
| 4,300 | 3,368 | 3,851 | 15초 | 포화 |
| 6,000 | 3,258 | 4,512 | 57초 | 포화 |
| 7,000 | 3,135 | 4,690 | 78초 | 포화 |

- 12 스레드 전부 활성 + 최적화로 rate 2,000 에서 앱 CPU 240–340%(Phase 1은 337%), load1 5–10(Phase 1은 9–13) — 건당 CPU 감소.
- realtime 소비는 여전히 ~3,100–3,400 에서 평평 → **Redis 커넥션 1개가 유일한 하드 실링**.
  12 컨슈머 스레드가 GET/SET/PUBLISH 를 단일 Lettuce 연결로 직렬화.
- Redis 는 `maxmemory 256MB` 에 상시 붙어 초당 ~2,000–2,600 키 축출 (누적 4,400만+).
  멱등성 키가 TTL 전에 축출돼 사실상 무력화.
- 측정 한계: 부하 3,000+ 구간에서 샘플러 curl 이 타임아웃해 timeline 의 CPU/lag 표본이 비었다
  (소비율·배수시간은 메인 루프에서 계측되므로 유효). 샘플러는 이후 커밋에서 보강.

## 다음 개선 (효과 큰 순서)

1. **`build.gradle` 에 `org.apache.commons:commons-pool2` 추가** → Lettuce 커넥션 풀 활성 →
   12 스레드가 Redis I/O 를 병렬로. 이후 `STOCKFLOW_OPT_REDIS_PIPELINE=true` 로 왕복 3→1회.
   → realtime 실링 2–3배 기대 (발표자료 §8 의 "폐기한 개선안"이 이 전제조건 하나 때문이었음).
2. **Redis `maxmemory` 상향**(256MB→2GB+) 또는 멱등성 키 TTL 축소 → 축출 폭주 해소.
3. 서버 NTP 동기화 → `stockflow_e2e_latency` 음수 문제 해결 ([GRAFANA_GAPS.md](GRAFANA_GAPS.md)).
4. (필요 시) storage/realtime 프로세스 분리 → CPU 경합 제거.
